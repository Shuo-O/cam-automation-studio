# CAM Automation Studio 产品与试点实施方案

> 面向台州黄岩模具企业的 PowerMill / Siemens NX 工作流智能化平台
>
> 方案版本：0.5.0 规划稿
>
> 证据日期：2026-08-23
>
> 建议周期：首轮 12 周

## 1. 执行摘要

CAM Automation Studio 的第一版不从“看屏幕、猜按钮、模拟点击”的通用代理开始，而是优先接入 PowerMill 宏与命令、PowerMill API 响应、NX Journal、NXOpen API、项目实体和软件实例信息。系统把高级程序员的真实操作整理为结构化事件，发现重复流程，生成可编辑配方，再针对明确的 PowerMill/NX 实例执行 dry-run 并返回差异。

第一版只承诺六件事：

1. 读：自动发现 PowerMill、NX 和 Codex 的连接及多个软件实例。
2. 记：插件安装后自动增量记录宏、Journal、命令、响应和结构化日志。
3. 筛：支持 `manual / automation / system / execution_audit` 模式筛选和 `L0-L4` 层级筛选。
4. 学：从多次会话中发现重复步骤、变量参数和流程分支。
5. 审：在配方编辑器和 Codex 审阅助手中解释来源、参数与差异。
6. 试：选择明确的软件实例和测试项目执行 dry-run，返回响应、耗时和对象变化。

首版不生成、后处理或发送机床可用 NC/G-code。学习结果是配方、宏草稿、NXOpen 预览和项目内 dry-run。

## 2. 产品目标

### 2.1 一句话定位

面向黄岩模具企业的 CAM 工作流副驾驶：从 PowerMill/NX 的结构化行为中学习专家经验，生成可回放、可参数化、可审阅、可定向 dry-run 的自动化配方。

### 2.2 用户价值

- 老板/厂长：看到重复编程活动、配方复用率和可量化节省时间。
- CAM 主管：整理企业工艺模板，比较不同程序员和不同版本的执行差异。
- 高级程序员：自动整理操作过程，减少手工编写宏、Journal 和培训材料的时间。
- 初级程序员：使用步骤化配方、参数说明和预览完成重复任务。
- 应用/质量人员：通过任务时间线、项目差异和仿真摘要定位问题。
- 数字化负责人：统一管理插件、软件版本、连接状态、性能和诊断。

### 2.3 五个产品决定

1. 结构化数据优先级为：原生 API/项目实体 > 命令与响应 > PowerMill 宏/日志 > NX Journal/NXOpen 事件 > 文件/进程元数据 > OCR/图像。
2. 基础软件保持小型化，默认只有插件中心、连接摘要、任务框架和诊断入口。
3. PowerMill、NX、本地记录、命令中心、Codex 审阅和版本适配包均作为可安装插件交付。
4. 本地记录插件安装后自动连接并开始记录；状态始终在主窗口可见，高级设置可分别暂停日志记录、窗口发现和命令记录。
5. 多个 PowerMill/NX 窗口统一显示在一个连接抽屉中，不为每个实例打开独立状态窗口。

## 3. 黄岩产业调研

### 3.1 已核验产业信号

| 已核验事实 | 产品含义 | 来源 |
|---|---|---|
| 黄岩约有 10 万模具从业者、4000 多家模具及相关企业，年产值接近 300 亿元 | 存在面向区域工艺复用和服务商生态的产品空间 | S3 |
| 区内有 180 余家设计、造型和编程服务企业 | 首批客户可同时覆盖工厂和区域编程服务商 | S3 |

### 3.2 待现场验证的需求假设

- 编程过程难以量化，管理者看得到交期和结果，看不到重复设置、回滚和等待。
- 高级程序员的动作顺序、参数选择和异常处理分散在个人宏、Journal 和操作习惯中。
- 同一操作者可能同时打开多个 PowerMill/NX 项目，连接和命令必须明确对应实例。
- CAM、文件、排产、仿真和质量系统已经存在，但缺少轻量的工作流整理层。
- 真正有价值的是高频流程复用，而不是通用聊天或大量页面。

本方案属于公开资料和案头研究，不声称已经完成黄岩工厂访谈。痛点优先级、定价、效率目标和成本必须通过 5-8 家现场样本继续验证。

## 4. 竞品与官方接口结论

### 4.1 PowerMill

- Autodesk 官方支持把用户操作录制为宏。
- 宏录制只保存用户在对话框中改变的值，默认值可能不会出现在宏中。
- Autodesk 官方示例展示 `PowerMill.dll`、`PluginFramework.dll`、COM 注册、`DoCommandEx` 和 `QueueCommand` 等形态。
- PowerMill 适配器应按目标版本验证实例选择、命令线程、超时、响应和项目实体。

### 4.2 Siemens NX / UG

- Siemens 提供按 NX 系列发布的 NXOpen Python Reference 和 Programmer's Guide。
- NX Journal 适合发现真实 NXOpen 调用，但录制对象标识需要转换为稳定名称、属性、PMI 或几何选择器。
- 目标 NX 安装自带 Python stubs 是最终接口依据。
- NX 专属解析保留在 `plugins/ug-cam-copilot/src/ugcam_ai/adapters/nx_journal.py`，不得混入 PowerMill 语法。

### 4.3 市场产品

| 产品 | 公开能力 | 值得吸收 | 本项目区别 |
|---|---|---|---|
| CloudNC CAM Assist | 嵌入现有 CAM，提供策略/刀路建议并支持 NX | 在宿主工作流内展示可编辑结果 | 第一阶段先学习工厂自己的专家操作 |
| OptiNC for PowerMill | PowerMill 插件，覆盖粗精加工、钻孔、3+2 和批量参数 | 把复杂能力包装为高频任务插件 | 先由真实行为频率决定模块优先级 |

竞品页面中的效率数字属于厂商声明，不作为本项目承诺。

## 5. 产品信息架构

### 5.1 首次使用

1. 用户打开基础软件，只看到连接摘要、插件中心、诊断和“未安装业务模块”的空状态。
2. 用户安装“PowerMill 学习”或“UG/NX 学习”插件，也可安装推荐组合。
3. 安装本地记录插件后，软件自动发现实例并开始记录，不弹出多步设置窗口。
4. 顶部连接条显示 `PowerMill 2`、`NX 3`、`Codex 1` 等摘要。
5. 用户进入日志中心，选择“仅手动 + L2 会话”，开始整理专家流程。

### 5.2 单窗口导航

| 区域 | 默认内容 | 主要操作 |
|---|---|---|
| 顶部连接条 | Codex、NX、PowerMill 摘要、记录状态 | 展开实例抽屉、固定任务目标 |
| 插件中心 | 已安装/可安装、依赖、版本、更新状态 | 安装、卸载、更新、推荐组合 |
| 工作台 | 日志、会话、学习、配方、命令、审阅页签 | 筛选、标注、比较、生成、运行 |
| 连接抽屉 | 产品、PID、项目、版本、前台、日志映射 | 校正未映射会话、选择目标实例 |
| 高级设置 | 记录开关、路径、性能、版本、诊断 | 暂停、重扫、重连、导出诊断 |

## 6. 日志模式与层级

模式和层级是两个互不影响的筛选维度。ActivityEvent 通过新增可选字段保持向后兼容。

### 6.1 来源模式

| `source_mode` | 含义 |
|---|---|
| `manual` | 用户在 PowerMill/NX 中直接操作或由软件原生录制的行为 |
| `automation` | 宏、Journal、插件或配方产生的动作 |
| `system` | 进程、窗口、文件发现、连接和状态事件 |
| `execution_audit` | 命令请求、响应、耗时和结果事件 |

### 6.2 学习层级

| `view_level` | 视图 | 内容 |
|---|---|---|
| `L0` | 原始证据 | 原文、时间、来源行、产品和实例 |
| `L1` | 规范动作 | `cam.*`、`nx.*`、`powermill.*` 动作 |
| `L2` | 会话 | 按任务、项目和实例组织的连续操作 |
| `L3` | 重复配方 | 跨会话重复结构、变量和支持度 |
| `L4` | 运行候选 | 参数、目标版本、目标实例和预览结果 |

建议新增的 ActivityEvent 可选字段：

```text
source_mode
view_level
expertise_label
instance_id
target_version
command_response
review_status
recipe_hash
```

共享动作继续使用 `cam.*`，产品专属动作分别使用 `nx.*` 和 `powermill.*`。

## 7. 系统架构

```text
PowerMill instances                         NX instances
  macro / command / API response              Journal / NXOpen
              |                                      |
              v                                      v
     PowerMill adapter                         NX adapter
              |                                      |
              +---------> ActivityEvent v1 <---------+
                              |
                   local event store + index
                              |
             +----------------+----------------+
             |                |                |
         log center     session timeline    diagnostics
             |                |
             +--------> workflow learning
                              |
                       recipe editor
                         |          |
                         v          v
                   Codex review   command center
                                      |
                           target instance + dry-run
                                      |
                            response + DiffReport
```

### 7.1 数据流水线

1. 采集：增量读取受支持日志，或接收 Journal/API/命令响应。
2. 规范化：保留来源文本，将动作映射为统一事件。
3. 会话化：根据产品、实例、项目、时间和显式标记组织会话。
4. 学习：发现重复序列，将跨会话变化的字面量提升为参数。
5. 编辑：工程师调整步骤、参数、条件、版本范围和说明。
6. 审阅：Codex 返回动作解释、差异、参数建议和待确认项。
7. 运行：选择目标实例和测试项目，生成 dry-run 与 DiffReport。

## 9. 核心模块说明

### 9.1 多软件连接中心

- 自动发现所有 PowerMill/NX 进程和可见窗口。
- 每个实例显示产品、PID、窗口标题、项目、版本、前台状态和连接响应。
- 无法确定会话归属时显示“未映射”，允许用户在同一抽屉校正。
- 每个实例使用独立任务队列，一个实例断连不阻塞其他实例。

### 9.2 日志中心与会话时间线

- 记录插件安装后默认自动工作。
- 支持模式、层级、产品、实例、项目、动作、时间和全文搜索。
- 表格采用虚拟滚动和分页，详情在右侧面板显示。
- 支持合并/拆分会话、标记专家示范、比较 2-5 个会话。

### 9.3 工作流学习与配方编辑

- 对选择的会话计算结构签名、重复序列、支持度和变量参数。
- 将返工、探索性步骤和稳定主流程分开显示。
- 配方编辑器采用三栏布局：步骤、参数/条件、来源/差异。
- 配方包含适用产品、软件版本、项目条件、参数类型、默认值和来源会话。

### 9.4 PowerMill 适配器

```text
discover_instances() -> [InstanceDescriptor]
connect(target_version, target_instance_id, read_only=True)
query(command) -> CommandResponse
record_macro(path) -> RecordingHandle
get_project_snapshot() -> SnapshotMetadata
preview(recipe, parameters) -> DiffReport
queue(command, run_context) -> CommandResponse
disconnect()
```

阶段路线：

- PM-0：`.mac / .log / JSONL` 离线解析、筛选和配方草稿。
- PM-1：PMAutomation / `DoCommandEx` 连接、项目查询和响应。
- PM-2：针对明确实例和测试项目执行 dry-run。
- PM-3：按场景交付钻孔、粗加工、精加工和批量参数插件。

### 9.5 NX 适配器

- NX-0：NX Open Python Journal / JSONL 静态解析，不导入或执行 Journal。
- NX-1：根据目标版本 Python stubs 查询会话、部件、对象和 CAM 设置。
- NX-2：在测试项目预览 NXOpen Builder 的对象和参数变化。
- NX-3：交付钻孔、工序、刀具、Teamcenter 等场景插件。

### 9.6 命令中心与 Codex

- 命令中心支持适配器定义的查询命令和从配方生成的 dry-run。
- 任务界面明确显示产品、PID、项目、版本、配方哈希和参数。
- 返回原始响应、结构化结果、耗时、对象变化和仿真摘要。
- Codex 接收结构化上下文包，返回 `findings`、`suggested_parameters` 和 `questions`。
- 用户可以逐项采用建议，不需要在聊天与工作台之间手工搬运信息。

## 10. 性能目标

| 路径 | 首版目标 | 工程方法 |
|---|---|---|
| 后台日志发现 | 新事件 2 秒内可见，平均 CPU < 2% | 增量 tail、退避扫描、可暂停 |
| 本地存储 | 100,000 事件导入 < 10 秒 | 批量事务、SQLite WAL、索引 |
| UI 查询 | p95 < 200 ms | 分页、虚拟滚动、预聚合 |
| 宿主查询 | 默认超时 5 秒，可配置 | 断路、重连、实例隔离 |
| 工作流学习 | 10,000 会话内结果确定 | 限制候选长度、后台任务 |
| 恢复 | 重启后不重复写入 | 游标、内容哈希、校验点 |

这些指标是首版工程目标，不是当前实测结果。必须在目标 PowerMill/NX 版本和真实项目规模上测量。

## 11. 12 周 MVP

| 周期 | 交付 | 验收 |
|---|---|---|
| 第 1-2 周 | 5-8 家工厂访谈、版本/日志/API 清单、基线 KPI | 至少 15 个真实会话样本 |
| 第 3-4 周 | PowerMill 只读连接 POC、宏录制与响应 | 两个版本、双窗口不串线 |
| 第 3-5 周 | NX 只读连接 POC、Journal 与 stubs 对照 | 两个版本、稳定对象样例 |
| 第 5-7 周 | `source_mode`、`view_level`、实例和自动记录 | 筛选准确率人工抽检通过 |
| 第 7-9 周 | 会话化、专家标签、重复配方和差异视图 | 三类高频候选流程 |
| 第 9-10 周 | Codex 审阅、命令中心、目标实例 dry-run | 超时、断连和恢复演练 |
| 第 11-12 周 | 两家样板试点、培训、性能和收益测量 | Go/No-Go 评审 |

### 11.1 最小演示

1. 从空白基础软件安装 PowerMill、UG/NX 和本地记录插件。
2. 自动显示两个 PowerMill 窗口、两个 NX 窗口和 Codex 状态。
3. 自动采集三次相似会话，筛选“仅手动 + L2 会话”。
4. 比较会话并生成重复配方，查看变量、来源、支持度和差异。
5. Codex 返回动作解释、参数建议和待确认项。
6. 选择明确的 `target_instance_id`，在测试项目执行 dry-run。
7. 显示响应、耗时、对象差异和仿真摘要。
8. 暂停记录后恢复，确认增量游标续接。

## 12. 现场试点和 KPI

首轮覆盖 5-8 家黄岩企业，每家观察至少一个真实编程任务；选择两个版本环境明确、重复流程具有代表性的企业进入 4 周试点。

| 指标 | 首轮假设 | 通过条件 |
|---|---|---|
| CAM 编程用时 | 降低 20%-35% | 两家样板厂同向改善 |
| 重复手工动作 | 降低 30%-50% | 不增加回滚率 |
| 配方复用率 | 达到 30%+ | 至少 3 类流程持续复用 |
| 回滚/重做率 | 降低 10%-20% | 按任务复杂度校正 |
| 交接时间 | 降低 20% | 任务状态完整率 100% |
| 实例映射准确率 | 达到 99%+ | 未映射事件可快速校正 |
| 后台性能 | 达到第 10 节预算 | 目标项目 p95 达标 |

这些改善幅度是产品假设，不是行业事实或销售承诺。

## 13. 现场访谈提纲

每家企业建议安排 60-90 分钟访谈和 90-180 分钟真实编程观察。围绕一个完整任务记录软件版本、项目规模、手工/自动步骤、等待、回滚、参数理由和可复用候选。

### 13.1 老板、厂长和 CAM 主管

1. 过去三个月最常延期的模具类型是什么，延误发生在哪个阶段？
2. PowerMill 与 NX 分别有多少席位、版本和常用插件？
3. 高级程序员每周用于重复设置、审阅、排障和带教的时间是多少？
4. 当前从 CAM 编程到提交仿真经过哪些角色和系统？
5. 哪些日志/API 能完整反映步骤，哪些关键动作没有结构化来源？
6. 企业愿意为什么结果付费：节省工时、降低返工、缩短交接、专家经验复用还是版本维护？

### 13.2 高级和初级程序员

1. 从空项目完成一个真实任务，并在关键参数处说明选择理由。
2. 哪些步骤每个项目都做，哪些步骤只适用于特定材料、模具、刀具或机床？
3. 最近一次撤销、重算或返工是什么原因，日志中能否看到？
4. 当前使用哪些宏、Journal、模板或脚本，哪些容易因版本或对象名失效？
5. 重复配方应优先展示来源、支持度、差异、版本还是参数说明？
6. 哪些动作适合一键运行，哪些需要逐步查看结果，哪些必须保留工程师判断？

### 13.3 应用、质量和数字化人员

1. CAM 项目提交后如何完成碰撞、过切、余量、刀具和后处理检查？
2. 异常发生时如何定位到项目、软件版本、命令和修改？
3. 工作站配置、PowerMill/NX 版本、COM 注册、Python 环境和升级窗口是什么？
4. 多窗口、远程桌面、Teamcenter 和共享目录如何影响项目识别？
5. 可接受的 CPU、内存、磁盘、查询延迟和恢复时间是多少？

## 14. Go / No-Go

- **Go**：至少三类流程在两家样板厂持续复用；连接、会话归属和 dry-run 结果可靠；KPI 同向改善。
- **Conditional Go**：效率有改善但版本适配成本高，缩小到一个产品和两个目标版本继续。
- **No-Go**：结构化数据覆盖不足、配方复用率低、实例映射长期不准，或收益主要来自一次性顾问配置。

## 15. 阶段路线

| 阶段 | 时间 | 产品结果 | 退出条件 |
|---|---|---|---|
| 0 离线底座 | 已完成 | 日志/Journal 学习、插件内核、dry-run、Codex 桥 | 当前仓库测试通过 |
| 1 只读连接 | 0-3 个月 | PowerMill/NX 版本化查询和自动结构化记录 | 多实例不串线、性能达标 |
| 2 目标 dry-run | 3-6 个月 | 测试项目中按实例运行已审阅配方 | 响应、差异、仿真和回滚验收 |
| 3 工厂工艺插件 | 6-12 个月 | 钻孔、粗加工、精加工和批量参数模块 | 稳定复用、工厂续约 |
| 4 模板生态 | 12 个月后 | 场景模板、版本适配包和区域服务商市场 | 模板复用、维护成本、伙伴收入 |

## 16. 产品实施难点

| 难点 | 影响 | 产品应对 |
|---|---|---|
| PowerMill/NX 版本差异 | 接口、对象名和响应不一致 | 版本适配包、目标 stubs、实机样本矩阵 |
| 日志不等于操作意图 | 重复动作可能来自返工或探索 | 项目实体、会话对比、专家说明和人工标签 |
| 后台记录性能 | 大项目下影响 CAM 交互 | 增量读取、WAL、分页和性能仪表盘 |
| 初次采用率 | 功能多但用户不形成日常习惯 | 安装后自动工作、默认视图和推荐组合 |
| 工厂定制过多 | 交付和维护成本失控 | 稳定插件接口、共性模块和参数化场景 |
| 模板持续维护 | 软件升级后配方逐渐失效 | 配方版本、来源样本和批量兼容检查 |

## 18. 开发边界

- ActivityEvent 只增加可选字段，不重命名或删除现有字段。
- PowerMill 解析进入现有 PowerMill 应用或独立 `powermill_macro.py`。
- NX 解析只保留在 `nx_journal.py`，不得为 PowerMill 修改该解析器。
- 共享动作使用 `cam.*`，产品专属动作使用 `nx.*` 或 `powermill.*`。
- 生成的生产动作保持 dry-run，直到配方经过人工复核并完成 CAM 仿真、碰撞检查和车间确认。
- 不从学习日志生成或发送机床可用 NC。
