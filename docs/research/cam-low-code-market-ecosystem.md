# CAM 低代码改编市场与生态预研

> 研究代号：R-MARKET
> 研究日期：2026-08-24
> 访问日期：2026-08-24
> 研究范围：PowerMill 宏/插件生态、Siemens NX Journal/NXOpen 生态、可解释低代码邻近产品、采用与授权/IP 边界、MVP 验证与产品合同输入
> 目标用户：已经购买商业 CAM 外挂，并积累 PowerMill 宏、NX Journal 或 NXOpen 自动化资产的模具刀路编程人员及其主管
> 文档性质：案头研究与产品假设，不构成法律意见、厂商授权或现场验证结论

## 1. 执行结论

### 1.1 核心判断

1. **[已验证事实] 用户已有资产是第一等产品输入，不是需要被替换的遗留负担。**
   PowerMill 官方支持把操作录制为可编辑宏，官方 API 与插件样例又提供宏命令、外部自动化、进程内插件和第三方工具接口等形态；NX 官方把 Journal 描述为可录制、可编辑、可加入逻辑和用户交互、直接作用于数据库的自动化工具。[S1][S3][S4][S6]

2. **[研究假设] 市场切入口不是再造一个“大而全自动编程外挂”，而是给已有宏、Journal、NXOpen 脚本和商业外挂增加可解释的资产盘点、参数化改编、版本证据、权限控制和多实例运行上下文。**
   OptiNC 已经把 PowerMill 高频流程包装成大量专用功能；CAM Assist 已经把策略和刀路生成嵌入多个 CAM。直接复制这些垂直能力既难形成差异，也容易触及客户既有采购、工艺和知识产权边界。[S11][S12]

3. **[已验证事实] “录制”不能等同于“完整意图”。**
   PowerMill 官方明确说明，宏只记录在对话框中被改变的值；已经处于目标值的默认项必须重新输入才会被记录。Microsoft Power Automate 也明确说明录制结果通常需要编辑，条件和循环不能被录制，录制中还可能存在冗余步骤。[S1][S13]

4. **[研究假设] 最可信的低代码形态是“证据驱动的可编辑配方”，不是不可见的自动化按钮。**
   每一步应显示原始来源、适用产品与版本、参数来源、依赖资产、目标实例、风险和不确定性；用户可以逐步采用、替换或禁用步骤。Node-RED 的 JSON 导入/导出和 Power Automate 的“录制后逐动作编辑”证明了可移植、可查看、可局部改编的交互模式具有邻近产品先例。[S13][S14]

5. **[已验证事实] 商业集成权利不能从“客户买过软件”自动推导。**
   Autodesk 2026 通用条款把订阅使用权、API 使用、商业软件开发、第三方材料和禁止逆向分别约束；其中商业 API 用途可能需要单独开发者许可。Siemens Digital Industries Software 则说明客户合同通常由订单、补充条款和基础条款共同组成。[S5][S8][S9]

6. **[研究假设] 产品必须把“授权依据”做成数据，而不是一次性的复选框。**
   每个导入资产和每个适配器都应记录来源、所有权/使用权声明、允许的用途、是否可团队共享、是否允许外发、适用席位/版本和授权证据引用；系统不得替客户判断其宏、Journal、商业外挂导出物能否再分发。

7. **[已验证事实] 当前仓库已经选择了正确的技术与安全底座。**
   基础内核默认不安装业务插件；NX 与 PowerMill 解析器物理隔离；共享动作使用 `cam.*`，产品专属动作使用 `nx.*` / `powermill.*`；生产动作保持 review-first 和 dry-run；不从学习日志生成或发送 machine-ready NC。[R1][R2][R4]

### 1.2 建议定位

**[研究假设] 推荐定位：**

> 面向已有 CAM 自动化资产的“可解释改编层”：在不读取商业二进制内部实现的前提下，把客户有权使用的 PowerMill 宏、NX Journal/NXOpen 脚本、命令日志和厂商授权能力清单整理为可追溯、可参数化、可审阅、可按实例 dry-run 的配方。

这个定位刻意避开三件事：

- 不声称替代 PowerMill、NX、OptiNC、CAM Assist 或其他商业外挂。
- 不通过反编译、注入、抓取私有协议或复刻隐藏算法获得能力。
- 不把日志学习结果直接转换成生产 NC、后处理输出或无人审批的 live 操作。

## 2. 研究方法与证据口径

### 2.1 证据等级

| 标签 | 定义 | 使用规则 |
| --- | --- | --- |
| **已验证事实** | 来自本仓库冻结合同、CAM 厂商官方文档、厂商官方开源仓库或可直接检查的原始资料 | 可以作为产品约束或验证前提，但仍需按目标版本复核 |
| **厂商主张** | 来自商业产品官网、案例、营销页或厂商自述的效率、安全、易用性和覆盖范围 | 只用于识别产品形态，不转写为本产品承诺 |
| **研究假设** | 根据证据推导、尚未通过目标用户访谈或现场试点验证的需求、指标、优先级与商业判断 | 必须进入访谈、可用性测试或试点验收 |

### 2.2 研究边界

- 只查阅公开文档、公开仓库、产品官网和仓库现有资料。
- 不下载、反编译、反汇编或动态分析任何商业 CAM 或商业外挂二进制。
- 不推断私有协议，不绕过许可证、席位、登录、联网验证或插件管理器。
- 不把公开样例的许可证外推到 PowerMill、NX 或第三方商业外挂本体。
- 不把厂商效率数字作为市场平均值或本产品 KPI 基线。
- 法律与许可结论只形成产品防线；真实合同解释由客户法务、采购和厂商授权文件决定。

## 3. 目标用户与现实工作

### 3.1 目标用户画像

**[研究假设] 主要用户不是“零自动化基础的新手”，而是已经形成混合自动化栈的模具 CAM 团队：**

- PowerMill 程序员保存了个人或部门 `.mac`、启动宏、模板、参数批处理宏和外挂生成结果。
- NX 程序员保存了录制 Journal、手写 NXOpen Python/VB/C#、Builder 调用片段、对象查找规则和 Teamcenter 运行约定。
- 团队已经购买一到多个商业外挂，用于钻孔、粗精加工、3+2、批量参数、NC 程序或工艺模板。
- 同一工作站或远程环境可能同时打开多个 PowerMill/NX 实例、项目和版本。
- 关键经验分散在脚本、目录结构、命名、刀具/模板库、外挂配置和高级程序员口头说明中。

### 3.2 用户当前要完成的工作

| 用户工作 | 当前资产/动作 | 典型摩擦 | 产品机会 |
| --- | --- | --- | --- |
| 找到可复用自动化 | 浏览个人目录、共享盘、外挂菜单、聊天记录 | 名称不一致，不知道适用版本和负责人 | 本地资产目录、哈希、版本、依赖和使用证据 |
| 判断宏/Journal 做了什么 | 打开文本、逐行阅读、在测试件试跑 | 默认值缺失、对象名脆弱、嵌套调用和副作用不透明 | 源码到规范动作映射、风险标记、依赖图 |
| 为新模具改参数 | 复制文件、搜索替换、手改路径/名称/数值 | 字面量与真正参数混在一起 | 基于多样本差异提议类型化参数 |
| 组合商业外挂与自有宏 | 先跑外挂，再手工补步骤或运行宏 | 外挂能力不可见、许可证和版本依赖未记录 | 只接能力清单/公开接口/厂商适配器，保留人工边界 |
| 给初级程序员复用 | 发文件、口头说明、远程演示 | 不知道为什么这么做，也不知道何时不能用 | 来源、适用条件、反例、审阅状态和预览 |
| 在多个 CAM 窗口间运行 | 看标题、切前台、凭经验选项目 | 任务串实例或日志归属不明 | 单窗口实例抽屉、显式目标绑定、不猜测歧义 |
| 应对 CAM 升级 | 逐个试宏和 Journal | API、命令、对象选择器、插件 DLL 随版本变化 | 版本能力清单、批量静态检查、测试矩阵 |

## 4. 现有 CAM 外挂、宏生态与资产形态

### 4.1 PowerMill 生态

#### 已验证事实

| 资产/接口形态 | 已验证事实 | 实际产品含义 | 来源 |
| --- | --- | --- | --- |
| 录制宏 | PowerMill 可在用户工作时录制命令；只记录在对话框中被改变的值 | 导入器必须把“未出现”解释为“未知/沿用上下文”，不能解释为默认值已确认 | [S1] |
| `.mac` 宏文件 | 官方帮助把宏作为可运行、可编辑、可组织的文件资产，并提供启动宏、嵌套宏等主题 | 资产盘点要支持文件、目录、嵌套引用、启动时机和外部路径，而不只是单文件命令列表 | [S2] |
| PowerMill API 库 | Autodesk 官方 MIT 仓库提供 PowerMill/PowerShape 自动化库，说明任务通过宏命令驱动，测试需要安装相应产品 | 公开库许可不等于宿主许可；版本与产品安装是运行前提 | [S3] |
| 进程内插件 | Autodesk 官方 Apache-2.0 样例需要目标安装中的 `PowerMill.dll`、`PluginFramework.dll`、COM 注册和 PowerMill Plugin Manager 启用 | 厂商授权适配器应声明目标版本、DLL 来源、注册状态和能力，不把 DLL 打包来源视为当然可再分发 | [S4] |
| 第三方工具接口 | 官方样例包括向 Vericut 等第三方应用导出数据的翻译器 | “通过受支持接口交换结构化数据”是可行生态形态，但每个第三方仍有独立条款 | [S4] |

#### 典型 PowerMill 资产包

**[研究假设] 一个真实可迁移资产不只是 `.mac` 文件，而应被视为：**

```text
宏正文
+ 被调用的子宏
+ 目录/环境变量约定
+ PowerMill 目标版本
+ 项目、模型、刀具、边界、模板和命名约定
+ 商业外挂前置/后置步骤
+ 操作者说明和已知反例
+ 试跑样本、仿真/碰撞证据
+ 所有权、共享范围和许可证证据
```

#### 典型 PowerMill 工作流

1. **[已验证事实]** 用户在 PowerMill 中通过官方宏录制入口完成一段操作。[S1]
2. **[研究假设]** 高级程序员打开 `.mac`，清理冗余命令，补充录制未捕获的默认值、条件和变量。
3. **[研究假设]** 宏引用项目实体、模板、刀具或其他宏，形成部门资产包。
4. **[研究假设]** 商业外挂处理某个高频阶段，程序员用自有宏完成前后处理和批量修改。
5. **[研究假设]** 升级 PowerMill、移动目录或更换项目命名后，宏通过试跑、手改和经验恢复。

### 4.2 Siemens NX 生态

#### 已验证事实

| 资产/接口形态 | 已验证事实 | 实际产品含义 | 来源 |
| --- | --- | --- | --- |
| NX Journal | Siemens 官方称 Journal 可录制交互、编辑、加入逻辑与用户交互，并直接作用于数据库而非依赖 UI | NX 适配应优先解析 NXOpen 调用和对象语义，不能用通用 UI 录制替代 | [S6] |
| NXOpen Python Reference | Siemens 文档按 NX 系列发布；本次可访问入口明确为 NX 2406 Series | 配方与适配器必须绑定目标系列，不能声明“NX 通用” | [S7] |
| NX 内置 Python | 开源 `nxlib` 说明 Journal 运行在 NX 内置解释器中，NX 2406 的示例环境为 Python 3.10，NX 侧代码没有第三方生产依赖 | 资产兼容检查要记录解释器版本、第三方依赖、NX/本地两侧执行位置 | [S10] |
| NX/Teamcenter 环境 | `nxlib` 的实际工作流区分 native 与 managed Teamcenter，会涉及 NX 安装、许可证、认证和环境变量 | 不能把 native 样本验证外推到 Teamcenter managed 环境 | [S10] |
| 本机 stubs | `nxlib` 从目标安装的 `%UGII_BASE_DIR%\UGOPEN\pythonStubs` 获取类型信息，并提醒类型提示并非绝对完整 | 本机目标版本 stubs 是能力核验输入，不是跨版本真理 | [S10] |

#### 典型 NX 资产包

**[研究假设] NX 自动化资产通常包括：**

```text
录制或手写 Journal
+ NXOpen Python/VB/C# 辅助库
+ 目标 NX 系列与内置解释器版本
+ 本机 pythonStubs / API 参考
+ native 或 Teamcenter managed 运行模式
+ 对象查找、命名、属性、PMI 或几何选择规则
+ CAM 模板、Operation/Tool/Method/Geometry 约定
+ 外部配置、环境变量与身份认证边界
+ 测试部件、预期对象差异和验证记录
+ 所有权、共享范围和许可证证据
```

#### 典型 NX 工作流

1. **[已验证事实]** 用户从 Developer 工具录制简单 Journal，再编辑为带逻辑和交互的脚本。[S6]
2. **[研究假设]** 程序员把录制产生的会话对象查找改为更稳定的名称、属性、PMI 或几何选择器。
3. **[研究假设]** 团队抽出可复用 NXOpen 函数，并按目标版本 stubs 调整 API。
4. **[研究假设]** native 与 Teamcenter managed 环境分别测试，记录许可证、认证、数据集和保存行为差异。
5. **[研究假设]** 升级 NX 后，用测试部件和对象差异重新验证，不直接在生产部件回放旧 Journal。

### 4.3 商业外挂的典型形态

| 形态 | 公开证据 | 证据类型 | 对本产品的含义 |
| --- | --- | --- | --- |
| PowerMill 内嵌功能插件 | OptiNC 宣称在 PowerMill 内提供 100 多项能力，覆盖自动刀路、钻孔、粗精加工、3+2、批量参数、托盘和 NC 程序等 | 厂商主张 [S12] | 不复刻隐藏逻辑；先识别外挂前后用户仍需手工完成的流程 |
| 多 CAM 嵌入式 AI | CAM Assist 宣称集成 Mastercam、NX、Fusion、GibbsCAM、SolidCAM 等，并让用户审查和调整策略后送回 CAM | 厂商主张 [S11] | 用户已接受“宿主内可编辑结果”；本产品应突出自有资产与本地控制 |
| 席位绑定 | CAM Assist 官网称按席位购买并绑定到 CAM 席位许可证 | 厂商主张 [S11] | 适配器状态要区分“已安装、已授权、席位可用、能力可用”，不能只有连接布尔值 |
| 云依赖 | CAM Assist 官网称需要稳定互联网连接，并使用云基础设施处理与生成策略 | 厂商主张 [S11] | 本地默认和显式外发授权可形成差异，但不能暗示云产品不安全 |
| 官方插件管理器 | PowerMill 官方样例要求 COM 注册后在 Plugin Manager 启用插件 | 已验证事实 [S4] | 产品插件中心不能替代宿主插件管理器；应展示两层状态与诊断 |

### 4.4 并行产品边界

**[已验证事实] 本仓库的并行边界必须保持：**

- NX Journal/NXOpen 语法只进入 `plugins/ug-cam-copilot/src/ugcam_ai/adapters/nx_journal.py`。
- PowerMill `.mac`、命令日志和产品语法进入 PowerMill 应用或独立 `powermill_macro.py`。
- 两个产品语义一致时使用 `cam.*`；产品专属动作使用 `nx.*` 或 `powermill.*`。
- 共享 session、recipe、query、permission、provenance 和 instance 层不解析任何产品语法。
- ActivityEvent 只能新增可选字段，不能删除、重命名或改变 v1 既有字段含义。
- 学习和生成结果始终 review-first；生产前仍需 CAM 仿真、碰撞/过切检查和车间批准。
- 不从学习日志生成、后处理、返回或发送 machine-ready NC/G-code。

## 5. 可解释低代码竞品与邻近产品

### 5.1 CAM 竞品

| 产品 | 公开能力 | 证据级别 | 可借鉴 | 不应照搬 |
| --- | --- | --- | --- | --- |
| CloudNC CAM Assist | 嵌入多个 CAM；配置刀具、材料、夹具和机床；生成策略；允许审查和调整；要求联网；按 CAM 席位授权 | 厂商主张 [S11] | 宿主内反馈、先配置上下文、生成结果可编辑、明确版本/席位 | “高达 80%”等效率数字；直接生成策略不是本项目首个差异点 |
| OptiNC for PowerMill | PowerMill 插件；大量面向钻孔、粗精加工、3+2、批量参数、托盘和模板的向导 | 厂商主张 [S12] | 高频场景插件化、低学习成本、能力清单 | 复制其功能和工作流；把厂商宣传效率当基线 |
| Autodesk 官方 PowerMill 插件样例 | 进程内插件、插件管理器、外部第三方翻译器、目标安装 DLL 和 COM 注册 | 已验证事实 [S4] | 厂商支持接口、能力与版本显式化、宿主内状态 | 打包或分析不具备再分发权的宿主 DLL |

### 5.2 邻近低代码产品

| 产品/模式 | 已验证事实 | 可迁移的交互原则 | CAM 限制 |
| --- | --- | --- | --- |
| Microsoft Power Automate Desktop | 录制器按 UI 元素生成独立动作；录制结束后可以逐动作编辑；多数录制流程仍需修改；条件/循环无法录制；可能产生冗余动作 | “录制是骨架”、步骤列表、局部编辑、录制缺口显式暴露 | UI 选择器不能表达 CAM 对象、刀路语义、默认参数和安全状态 [S13] |
| Node-RED | 流程可用 JSON 导入/导出；支持选中节点、当前流程或完整配置；可格式化为人可读 JSON | 可移植配方、局部导出、格式化 diff、本地库和示例库 | 通用节点图容易把 CAM 上下文压扁为字符串；必须保持类型化产品 adapter [S14] |
| NX Journal | 先录制，再编辑并加入逻辑/交互；直接作用于 NX 数据库 | 从真实工作生成可编辑自动化，并保留宿主对象语义 | 对象选择器、版本和执行副作用必须单独审查 [S6] |
| PowerMill Macro | 工作时录制命令，之后运行和编辑宏 | 从真实操作起步，文本资产适合 diff 与参数化 | 未改变的默认值不会被录制，不能把日志当完整状态 [S1][S2] |

### 5.3 推荐的低代码交互

**[研究假设] 一个适合资深 CAM 程序员的改编界面应当是“源证据 + 配方 + 预览”三栏，而不是自由画布优先：**

| 区域 | 默认显示 | 用户动作 |
| --- | --- | --- |
| 左栏：来源资产 | 宏/Journal 文件、来源行、会话、版本、依赖、授权状态 | 选择证据、比较样本、查看未支持内容 |
| 中栏：配方步骤 | 规范动作、产品动作、条件、参数、风险、禁用状态 | 重排、分组、启停、插入人工检查点 |
| 右栏：解释与预览 | 为什么成为参数、适用版本、目标实例、静态差异、门禁 | 接受/拒绝建议、补说明、选择测试项目 |

不建议首版使用无限画布作为主工作区，原因是目标用户的核心任务是逐行核对、比较差异和快速修改，而不是从空白节点图搭建通用集成。

### 5.4 可解释性的最低标准

**[研究假设] 每个生成步骤至少回答：**

1. 来自哪个文件、会话和来源行？
2. 是 PowerMill、NX 还是共享 `cam.*` 动作？
3. 哪些字面量被提升为参数，依据了几个独立会话？
4. 哪些默认值、对象状态或商业外挂内部步骤不可见？
5. 适用于哪些 CAM 版本、运行模式和资产依赖？
6. 是否需要商业外挂许可证或厂商授权适配器？
7. 将绑定哪个 `target_instance_id`、项目和 recipe hash？
8. 当前只允许静态预览、只读查询还是 dry-run？
9. 哪些仿真、碰撞、过切和车间门禁尚未运行？
10. 用户撤销某类授权后，哪些证据或能力立即不可用？

### 6.2 首次价值路径

**[研究假设] 首次使用不应要求连接 live CAM：**

1. 安装 PowerMill 或 NX 对应的离线资产插件。
2. 展示一次本地授权摘要，默认不允许网络外发和 live 执行。
3. 用户选择一个自己有权使用的宏/Journal 目录。
4. 本地扫描产生资产清单：类型、哈希、目标版本线索、依赖、嵌套调用、风险和不可解析项。
5. 用户选择 2-5 个同产品、同任务样本。
6. 系统生成可追溯配方候选，明确缺失默认值和对象选择器风险。
7. 用户在不连接 CAM 的情况下完成第一轮参数化和审阅。

**验证门槛假设：** 60 分钟可用性测试中，目标用户在不接受培训的情况下，应在 30 分钟内找到一个有价值的候选，并能正确说出“系统知道什么、缺什么、不会执行什么”。

## 7. 一次授权、分类撤销与本地数据控制

### 7.1 授权原则

**[研究假设] “一次授权”应表示一次清楚、版本化、可撤销的本机授权，不表示永久同意所有未来能力。**

- 安装插件与授予数据权限是两个事件。
- 首次授权可采用推荐组合，但必须列出每个类别。
- 新增权限类别、扩大外发范围或从只读升级到 dry-run 时必须再次授权。
- 撤销某一类别不删除其他类别的授权，也不隐式删除已保存数据。
- 删除本地数据是独立、高摩擦、可审计的动作。
- 卸载插件不等于删除数据；重新安装不得恢复曾撤销的授权。
- 总撤销应立即停止窗口发现、日志采集和新任务，并清空内存中的临时窗口元数据。

以上与当前仓库 README/架构的授权语义一致。[R2][R3]

### 7.2 建议权限分类

| 类别 | 允许内容 | 默认 | 撤销后的立即效果 |
| --- | --- | --- | --- |
| `asset_file_read` | 读取用户明确选择的 `.mac`、`.log`、Journal、JSONL 和配置清单 | 首次选择目录时授权 | 停止新扫描；保留已索引的脱敏元数据，除非用户另行删除 |
| `instance_discovery` | 读取支持的进程、PID、可见窗口句柄、临时标题和前台状态 | 推荐开启 | 停止枚举并清空内存窗口标题；现有事件不补删 |
| `project_metadata_read` | 通过授权 adapter 读取项目 ID、版本和只读实体摘要 | 关闭，连接时授权 | 断开该类查询，保留审计记录 |
| `execution_audit` | 记录请求、目标实例、拒绝原因、响应摘要和耗时 | 安装执行网关的强制依赖 | 禁止新执行任务；历史审计按保留策略处理 |
| `commercial_adapter_use` | 调用一个明确供应商、版本、席位和能力范围的授权 adapter | 逐 adapter 关闭 | 立即断开，不影响离线资产 |
| `codex_context_export` | 导出经过预览和脱敏的结构化审阅包 | 关闭 | 停止新导出，不影响本地审阅 |
| `network_egress` | 允许指定插件向指定域名发送列明的数据类别 | 默认关闭 | 阻断新外发；记录被拒请求 |
| `dry_run_transport` | 在明确测试项目和实例上提交已审阅配方预览 | 关闭 | 取消未开始任务，运行中任务按 transport 能力请求取消 |

### 7.3 数据控制产品要求

| 要求 | 可验证行为 |
| --- | --- |
| 本地默认 | 新安装且未授权外发时，资产内容和事件不离开本机 |
| 数据最小化 | 窗口标题只用于临时连接状态，不写入 ActivityEvent、配方或导出 |
| 路径脱敏 | 绝对路径在持久化前转换为安装内稳定伪匿名标记 |
| 外发预览 | 每次首次导出某类上下文前展示字段清单、条目数、大小、目的地和脱敏结果 |
| 分类撤销 | 撤销后不再产生该类别的新事件；诊断页显示停止时间和最后事件游标 |
| 分离删除 | “停止采集”“撤销授权”“清除本地数据”“卸载插件”是四个不同动作 |
| 可携带导出 | 用户可导出自己的结构化资产和审计记录，但需保留权限/来源元数据 |
| 无静默训练 | 未经单独明确约定，不把客户资产用于跨客户模型训练或公共模板 |

### 8.2 产品不可替客户推定的事项

**[研究假设] 以下事项必须由客户、供应商或法务给出证据，产品只能记录：**

- 宏/Journal 是员工职务成果、客户自有资产、供应商交付资产还是个人外部来源。
- 资产是否允许在同一法人、同一站点、外包编程人员或关联公司之间共享。
- 商业外挂是否允许通过公开 API 自动调用、批量调用或由另一插件编排。
- 目标安装中的 DLL、type library、stubs、模板和示例是否允许复制或再分发。
- 由外挂导出的宏、日志、报告、能力清单和中间文件是否可用于派生配方。
- 客户与供应商的保密协议是否限制日志、项目、刀具库、模板和性能数据外发。
- 许可证是否按用户、席位、设备、并发实例、站点、版本或订阅期限约束。
- 客户是否允许把内部配方发布到跨客户模板市场。

### 8.4 建议的客户声明

**[研究假设] 每次首次导入一个资产来源时，产品应保存以下声明，而不是只弹“我同意”：**

这不是法律结论，而是让权利来源进入审计链的产品机制。

## 9. 可验证 MVP

### 9.1 MVP 要证明的价值

**[研究假设] 首个市场 MVP 不需要证明“自动生成最优刀路”，需要证明：**

1. 用户能低成本找到并理解已有自动化资产。
2. 系统能把 2-5 个同产品样本整理为可解释、可参数化的配方候选。
3. 系统能明确暴露录制缺口、对象选择器、版本、依赖、权限和商业外挂边界。
4. 用户能在一个窗口内区分多个 CAM 实例，并把预览绑定到正确实例和测试项目。
5. 用户能随时撤销某类采集/连接/外发授权，且本地数据行为可验证。
6. 全流程不分析商业二进制、不生成 machine-ready NC、不越过 dry-run 与人工门禁。

### 9.2 MVP 用例

#### UC-1：资产体检

- **输入：** 一个用户明确选择且有权处理的 PowerMill 宏目录或 NX Journal/NXOpen 目录。
- **输出：** 资产清单、哈希、类型、版本线索、依赖、嵌套引用、危险命令、绝对路径、不可解析内容和授权状态。
- **价值假设：** 高级程序员不需运行资产即可识别优先维护对象。
- **通过条件：** 人工抽检 30 个资产；文件发现率 100%，已支持引用发现率不低于 95%，所有未支持内容均显式列出。

#### UC-2：同任务多样本参数化

- **输入：** 2-5 个同产品、同任务、不同零件/参数的宏或 Journal。
- **输出：** 共同步骤、变量候选、类型、支持度、来源行、差异和待确认问题。
- **价值假设：** 比复制搜索替换更快、更可审阅。
- **通过条件：** 每个生成步骤 100% 可追溯；错误合并产品或实例为 0；参数建议精确率经专家标注达到 80% 以上。

#### UC-3：PowerMill 录制缺口提示

- **输入：** 录制宏与一份可选的项目/对话框状态清单。
- **输出：** “未出现不等于默认已确认”的缺口提示、依赖状态和需人工补录项。
- **价值假设：** 降低宏在新项目上沿用错误默认值的风险。
- **通过条件：** 预设 20 个“值未改变因而未录制”样本全部标为 `unknown/requires_confirmation`，不自动填值。

#### UC-4：NX 对象选择器审查

- **输入：** 录制或手写 NX Journal，以及目标版本 stubs/能力清单。
- **输出：** 脆弱会话 ID/`FindObject` 线索、稳定选择器建议、API/解释器版本差异和静态预览。
- **价值假设：** 提前发现升级或换件后失效点。
- **通过条件：** 在两组目标版本 fixture 中，所有预设脆弱选择器被检出；系统不执行 Journal。

#### UC-5：商业外挂共存清单

- **输入：** 用户填写或厂商签名的外挂能力清单、版本、席位模型和允许的导出接口；可选外挂导出宏/日志。
- **输出：** 配方中标注“由外挂完成/不可见/需许可证”的步骤和人工接力点。
- **价值假设：** 不替换外挂，也能减少外挂前后手工衔接和知识断层。
- **通过条件：** 未授权能力不可调用；没有能力清单时系统只允许人工步骤占位，不猜测内部动作。

#### UC-6：多实例目标绑定

- **输入：** 两个 PowerMill 和两个 NX fixture 实例，以及若干可映射/不可映射会话。
- **输出：** 单窗口连接抽屉、显式目标实例、未映射提示、每实例独立队列。
- **价值假设：** 多窗口用户不需要切换多个状态窗口，也不会把前台窗口当默认目标。
- **通过条件：** 1,000 个 fixture 任务跨实例串线为 0；无法可靠映射的会话 100% 保持未映射。

#### UC-7：分类撤销和外发证明

- **输入：** 已开启的文件读取、实例发现、项目元数据、审计和 Codex 导出权限。
- **输出：** 逐类撤销、总撤销、最后事件时间、被拒外发审计和数据保留说明。
- **价值假设：** 本地控制是愿意安装后台记录插件的前提。
- **通过条件：** 撤销后 2 秒内停止新采集；默认网络外发为 0；重新安装不恢复曾撤销授权。

### 9.3 最小演示闭环

1. 从空白基础内核安装 PowerMill 与 NX 离线资产插件。
2. 逐类显示权限，用户一次确认本地文件读取和实例发现；网络外发保持关闭。
3. 导入三个 PowerMill 宏样本和三个 NX Journal 样本。
4. 资产体检报告显示嵌套引用、路径、版本线索、NX 选择器和未支持内容。
5. 分别生成 PowerMill 与 NX 配方候选；两者共享 UI 和合同，但不共享 parser。
6. 在配方中插入一个“商业外挂步骤”，只引用能力清单，不读取外挂二进制。
7. 用户逐项接受参数、补充默认值和适用条件，生成稳定 recipe hash。
8. 单窗口连接抽屉显示两个 PowerMill、两个 NX fixture 实例。
9. 用户选择明确测试项目和 `target_instance_id` 运行静态预览/dry-run。
10. 结果展示来源、对象差异和未运行门禁；不产生 NC/G-code。
11. 用户撤销实例发现与 Codex 导出，诊断页证明采集和外发停止。

## 10. 失败模式与防线

| 失败模式 | 证据级别 | 可能后果 | MVP 防线 |
| --- | --- | --- | --- |
| PowerMill 宏漏掉未改变默认值 | 已验证事实 [S1] | 在新项目沿用错误状态 | 缺失值标未知；要求显式状态样本或人工确认 |
| 录制含冗余步骤且不能表达条件/循环 | 已验证事实 [S13] | 配方冗长、错误参数化 | 多样本对比；人工删除；条件只作为审阅候选 |
| 宏调用子宏、外部程序或绝对路径 | 研究假设 | 依赖丢失、越权和副作用 | 依赖图；外部进程/嵌套执行风险门禁；不自动运行 |
| Journal 使用不稳定会话对象 ID | 研究假设，符合现有提案 | 换件或重开会话后失败 | AST 静态提示；稳定选择器建议；目标版本 stubs |
| NX 内置 Python 与本地 Python 不同 | 已验证事实 [S10] | 第三方库不可用、版本错误 | 记录运行侧、解释器和依赖；静态兼容检查 |
| native 样本被误用于 Teamcenter managed | 已验证事实/研究推导 [S10] | 认证、保存和对象行为不同 | 运行模式进入资产和配方适用条件 |
| 商业外挂步骤不可见 | 研究假设 | 系统编造或重复其内部动作 | 只用人工步骤/能力清单/厂商 adapter；不推断内部逻辑 |
| 客户没有资产再分发权 | 已验证事实/研究推导 [S5][S8] | 合同和 IP 风险 | 权利声明、共享范围、导出阻断、法律复核标记 |
| 许可证席位或订阅失效 | 厂商主张与合同结构 [S5][S11] | 连接可见但能力不可用 | 分离 installed/connected/licensed/capable 状态 |
| 多 CAM 实例日志归属不明 | 已验证仓库约束 [R2] | 串实例或错误项目 | 不猜测；人工映射；运行时五元绑定 |
| 用户以为 dry-run 等于加工批准 | 已验证仓库约束 [R4] | 跳过仿真和车间审批 | `not_run/required` 明示；生产批准不在 MVP |
| 网络外发泄露项目和工艺 | 研究假设 | 商业秘密或客户数据泄露 | 本地默认、字段级预览、域名白名单、分类撤销 |
| UI 录制被当作主证据 | 邻近产品已知局限 [S13] | 按钮变化、焦点和窗口错误 | 原生 API/对象/命令优先；UI/OCR 仅作为低置信度补充 |
| 版本升级后 adapter 静默降级 | 已验证版本依赖 [S4][S7][S10] | 错误结果却显示成功 | fail-closed 能力协商；未知版本只允许离线静态分析 |

## 11. 非目标

以下均不属于市场 MVP：

- 不反编译、反汇编、解密、注入或动态分析 PowerMill、NX 或任何商业外挂二进制。
- 不绕过许可证、席位、订阅、登录、网络验证、Plugin Manager 或厂商技术保护。
- 不复刻 OptiNC、CAM Assist 或其他商业外挂的隐藏算法、UI、模板库或受保护工作流。
- 不从屏幕像素、OCR 或鼠标轨迹推断商业外挂内部语义。
- 不替用户判断宏、Journal、模板、DLL、stubs 或导出物的所有权和再分发权。
- 不建立跨客户默认共享的宏/Journal 市场。
- 不自动上传客户项目、日志、刀具库、模板或配方用于跨客户训练。
- 不承诺自动生成最优刀路、进给转速、夹具、后处理或可生产 NC。
- 不生成、后处理、返回或发送 machine-ready NC、G-code 或机床控制指令。
- 不把 dry-run、静态预览或 Codex 审阅表述为 CAM 仿真、碰撞检查或车间批准。
- 不让 NX 输入进入 PowerMill parser，也不让 PowerMill 输入进入 NX parser。
- 不在共享 session/recipe 层解析产品语法。
- 不以自动前台窗口选择替代显式 `target_instance_id`。
- 不在 MVP 中承诺 live 生产执行。

### 12.3 试点实验

#### 实验 A：资产盘点价值

- 参与者：3 名 PowerMill、3 名 NX 高级程序员。
- 每人提供 10-30 个有权使用的历史资产。
- 对照：人工文件浏览与现有说明。
- 测量：找到适用版本、依赖、危险步骤和负责人所需时间。
- Go：至少 5/6 参与者更快完成盘点，且没有静默遗漏已支持风险。

#### 实验 B：解释与改编

- 参与者：每个产品 2 名高级、2 名初级程序员。
- 任务：把同一流程的 3 个样本改编到一个新测试件。
- 对照：复制、搜索替换和口头指导。
- 测量：完成时间、错误参数、求助次数、对来源解释正确率。
- Go：两产品均同向改善，且没有增加错误预览。

#### 实验 C：商业外挂共存

- 参与者：至少 2 家已购买商业外挂的企业。
- 任务：只使用公开导出、能力清单或厂商授权 adapter 描述外挂前后流程。
- 测量：可见人工接力点、重复手工步骤、许可证状态理解。
- Go：不分析二进制也能识别至少一个高频衔接流程；否则缩小该机会。

#### 实验 D：授权与撤销理解

- 参与者：程序员、CAM 主管、IT/数字化负责人各至少 2 人。
- 任务：完成首次授权、撤销窗口发现、撤销外发、删除本地数据。
- 测量：能否区分暂停、撤销、删除、卸载；撤销后系统实际行为。
- Go：所有参与者能正确预测行为；系统验证无未授权新事件或外发。

### 13.2 推荐切入顺序

1. **P0-A：离线资产体检。**
   最小授权、最快价值、最低现场依赖，同时为后续所有能力建立来源和权利元数据。

2. **P0-B：同产品多样本解释与参数化。**
   直接服务已有宏/Journal 用户，形成区别于垂直刀路外挂的核心价值。

3. **P0-C：权限、多实例和版本上下文。**
   把信任、正确目标和兼容性变成产品能力，不留到 live 接入后补做。

4. **P0-D：商业外挂能力清单。**
   先允许用户把外挂当作“有许可证的黑盒步骤”放入配方，不要求深度集成。

5. **P1：厂商授权 adapter。**
   只有供应商或合同明确授权时，才把黑盒步骤升级为可查询的结构化能力。

## 15. 产品形态启示

### 15.1 插件化

- **[已验证事实]** PowerMill 官方生态本身存在插件管理器、目标 DLL、COM 注册和第三方翻译器形态。[S4]
- **[研究假设]** CAM Automation Studio 应把产品 parser、资产扫描、商业 adapter、Codex 导出和执行网关拆为不同插件与权限类别。
- **[研究假设]** 插件中心显示的是 Studio 层安装状态；宿主内插件状态、许可证状态和能力状态必须分栏显示，不能合并成“已连接”。
- **[研究假设]** 版本适配包应是声明式 manifest + adapter，不应把产品语法复制到共享内核。

### 15.2 单窗口

- **[研究假设]** 目标用户需要在一个顶级窗口内完成资产、会话、配方、连接、权限和诊断，而不是为每个 CAM 实例打开一个控制窗口。
- 连接摘要负责快速判断“PowerMill 2 / NX 3 / 记录已暂停”；连接抽屉负责实例详情和目标校正。
- 配方编辑与实例选择在同一上下文中，但默认不自动选择前台实例。
- 商业外挂步骤以图标、供应商、版本和许可状态显示，不把其 UI 嵌套进 Studio。

### 15.3 多 CAM 实例

- **[已验证事实]** 当前仓库已采用产品、PID 和窗口句柄组成运行期实例 ID，并在无法把日志映射到多个窗口时不猜测。[R2][R3]
- **[研究假设]** 状态模型至少区分 detected、connected、licensed、capable、authorized 和 busy。
- 每实例独立串行队列；一个实例断连不阻塞其他实例。
- 会话不跨产品或实例；需要跨软件协作时使用上层“人工工作包”，不能合并为一个 parser session。
- 窗口标题仅临时显示；持久化使用不透明实例/项目 ID 和脱敏标签。

### 15.4 本地数据控制

- **[厂商主张]** CAM Assist 要求稳定联网并使用云基础设施，同时宣称对传输和静态数据加密。[S11]
- **[研究假设]** 对拥有敏感模具项目和自有工艺资产的用户，本地默认、明确外发预览和分类撤销可构成重要差异点。
- 这一差异点应以可验证网络审计和数据流说明表达，不能用“云不安全”式比较宣传。
- 本地模式仍需处理宿主厂商自身的订阅验证、Teamcenter、共享盘和企业安全策略；“本地”不等于“无任何网络依赖”。

## 16. Go / No-Go

### Go

- 两个产品各至少有 3 类真实资产能被稳定盘点、解释和追溯。
- 2-5 个同产品样本能够生成专家认可的参数化候选。
- 至少两家已购买商业外挂的企业愿意用能力清单/人工步骤描述共存流程。
- 用户理解并信任分类授权、撤销和本地外发控制。
- 多实例 fixture 和现场只读 POC 不串线，不可靠映射保持未映射。
- 全流程没有二进制分析、许可绕过或 machine-ready NC 输出。

### Conditional Go

- 资产体检有价值，但自动参数化精确率不足：先交付资产治理和版本审查。
- PowerMill 或 NX 一侧证据明显更强：保持合同并行兼容，但商业试点聚焦一个产品。
- 商业外挂厂商不提供 adapter：保留能力清单和人工步骤，不做深度编排。
- 本地部署成本高：缩小到单机离线扫描，不扩大网络和 live 权限。

### No-Go

- 用户已有资产数量少，核心价值主要来自重新定制外挂。
- 大部分关键流程只存在于不可导出的商业外挂内部，公开接口和厂商合作都不可得。
- 用户不能或不愿确认资产权利来源，组织也不允许本地索引。
- 配方解释不能可靠暴露未知状态，用户把候选误认为可生产结果。
- 价值必须依赖反编译、私有协议、许可证绕过或自动生成 machine-ready NC 才成立。

## 17. 结论

**[研究结论]** 市场上已经存在强大的 CAM 自动编程外挂，也存在成熟的 PowerMill 宏和 NX Journal/NXOpen 用户生态。CAM Automation Studio 的可防守机会不在于复制这些外挂，而在于成为已有资产之间的“可解释改编与治理层”：

- 尊重用户已经购买的商业能力和积累的源码资产。
- 只通过公开接口、用户有权导出的宏/日志、能力清单或厂商授权 adapter 集成。
- 用来源、差异、版本、权限和实例上下文解释每个配方步骤。
- 让离线资产体检先产生价值，再逐步升级到只读查询和明确测试项目 dry-run。
- 把一次授权、分类撤销、权利证据和本地外发控制做成可验证合同。
- 始终保持 NX/PowerMill parser 隔离、review-first、安全门禁和禁止 machine-ready NC 的仓库边界。

下一阶段最有价值的工作不是扩大实现面，而是用真实目标用户验证三件事：他们是否愿意把已有资产目录交给本地扫描；资产解释是否比人工盘点明显更快；以及在不分析商业外挂内部实现的情况下，能力清单和人工接力点是否足以形成可付费价值。
