# CAM Automation Studio 程序员开发者审核任务书

> 审核对象：AI 按 `T00-T15` 提交的实现
>
> 执行入口：[AI 执行任务书](./cam-automation-studio-ai-execution-taskbook.md)
>
> 产品依据：[CAM Automation Studio 产品方案](./cam-automation-studio-huangyan-product-proposal.md)

## 1. 审核目标

开发者不是只检查“测试是否为绿色”，而是确认：

1. 行为符合产品任务和真实 CAM 工作流。
2. PowerMill 与 NX 的实现边界没有被破坏。
3. ActivityEvent、HTTP API、插件 manifest 和 Skills 保持一致。
4. 多实例情况下没有把事件、项目或命令归到错误窗口。
5. 性能预算、错误状态和恢复路径可以在目标环境复现。
6. AI 没有删除测试、降低断言或用 fixture 掩盖未实现能力。
7. 变更可以独立回滚，不包含无关重构。

## 2. 审核结论

每个任务只能使用以下结论：

| 结论 | 含义 |
|---|---|
| `ACCEPT` | 功能、代码、测试和证据均满足任务 |
| `ACCEPT_WITH_FOLLOWUP` | 当前范围可合并，后续项不影响正确性且已建任务 |
| `CHANGES_REQUESTED` | 存在可修复问题，退回同一任务 |
| `BLOCKED` | 依赖真实软件、版本、许可证或样本，当前无法完成 |

禁止使用“基本可以”“看起来没问题”等模糊结论。

## 3. 缺陷等级

| 等级 | 定义 | 处理 |
|---|---|---|
| P0 | 可能串实例、破坏事件合同、执行错误目标或生成机床 NC | 禁止合并 |
| P1 | 核心功能错误、数据丢失、无法恢复、明显性能退化 | 禁止合并 |
| P2 | 边界状态、可维护性、诊断或重要测试缺口 | 修复后合并，或明确 follow-up |
| P3 | 文案、局部样式或非阻塞改进 | 可记录后合并 |

## 4. 通用审核流程

### 4.1 读取范围

```powershell
git status --short --branch
git diff --stat <base>...HEAD
git diff --check <base>...HEAD
git log --oneline <base>..HEAD
```

审核者必须先确认：

- 提交与任务 ID 对应。
- 没有意外二进制文件、缓存、数据库、构建目录或本机路径。
- 没有回退用户在任务开始前已有的修改。
- 没有将多个无关任务塞入同一提交。

### 4.2 代码审查

- 先看模型和接口变化，再看调用方，最后看 UI。
- 检查错误路径、取消、超时、重启和重复请求。
- 检查确定性：相同输入是否得到相同事件、会话、配方和 hash。
- 检查多实例：所有状态和任务是否携带 `instance_id`。
- 检查版本：PowerMill/NX 宿主调用是否显式绑定 `target_version`。
- 检查测试：是否覆盖行为，而不是只覆盖实现细节。

### 4.3 自动验证

根仓库最低验证：

```powershell
python -m unittest discover -s tests -v
```

UG/NX 插件最低验证：

```powershell
python -m unittest discover -s plugins/ug-cam-copilot/tests -v
```

按任务补充：

- Python 语法/类型检查。
- JSON Schema 与 manifest 校验。
- HTTP API 合同测试。
- 大日志和多实例性能测试。
- 桌面/移动浏览器截图和交互检查。

### 4.4 人工验证

每个 UI 任务至少检查：

- 1280×720 桌面视口。
- 1920×1080 桌面视口。
- 390×844 移动视口。
- 加载、空、错误、断连、超时和无匹配状态。
- 文本、按钮、抽屉、表格、提示和进度无重叠。

## 5. 不可变代码边界

以下条件任一不满足，直接 `CHANGES_REQUESTED`：

- ActivityEvent 现有字段被重命名、删除或改变含义。
- PowerMill 语法写入 `nx_journal.py`。
- NX 专属动作不使用 `nx.*`，PowerMill 专属动作不使用 `powermill.*`。
- 共享动作没有使用 `cam.*`。
- Journal 通过 `exec`、`import` 或子进程运行。
- 学习结果生成或发送机床可用 NC。
- 生产动作绕过 dry-run、CAM 仿真、碰撞检查或现场确认。
- 多实例命令可以在没有 `target_instance_id` 时选择前台窗口。

| T07 | 平台/产品 | sessionization | 会话归属可解释 |
| T08 | 算法/应用 | learning/mining | 结果确定、参数正确 |

## 7. 分任务审核清单

### T00 基线与合同固定

- [ ] 基线提交不改变运行行为。
- [ ] 路由、状态码、事件字段和插件依赖来自代码，不是推测。
- [ ] 根仓库与 UG 插件测试命令可复现。
- [ ] 文档标明当前未连接真实 PowerMill/NX live 传输。
- [ ] 基线提交可以作为后续性能和行为对照。

**退回条件**

- 测试数量或 API 清单与代码不一致。
- 把未来设计写成已经实现。

### T01 插件内核与插件中心

- [ ] 空安装注册表只加载基础内核。
- [ ] 插件依赖解析是确定性的。
- [ ] 安装失败不会留下半安装状态。
- [ ] 卸载依赖中的插件会返回可操作错误。
- [ ] 推荐组合没有绕过单插件 manifest。
- [ ] UI 不打开多个顶级窗口。
- [ ] 重新启动后安装状态正确恢复。

**重点测试**

```powershell
python -m unittest tests.test_plugin_manager tests.test_integrations -v
```

### T02 ActivityEvent 可选扩展

- [ ] 所有新增字段都是可选字段。
- [ ] 旧 JSONL fixture 无修改即可导入。
- [ ] 新字段可以序列化往返。
- [ ] 缺失值有明确、稳定的默认行为。
- [ ] Schema、根模型和 UG 模型含义一致。
- [ ] `source_mode` 和 `view_level` 没有互相推导。
- [ ] 产品动作前缀符合代码边界。

**P0 检查**

比较变更前后 schema；任何删除、必填化或语义变更必须阻止合并。

### T03 多实例连接中心

- [ ] 进程实例和窗口实例的 ID 规则明确。
- [ ] 重扫时未变化实例 ID 不漂移。
- [ ] 无窗口 CAM 进程仍可见。
- [ ] 多窗口数量和产品聚合正确。
- [ ] `unmapped` 不被前台窗口替换。
- [ ] 单实例断连不会清空全部产品状态。
- [ ] API 与 UI 使用同一个实例列表。

**人工场景**

1. 两个 NX 进程。
2. 一个 PowerMill 进程包含两个窗口。
3. 一个无标题/无前台窗口的进程。
4. 关闭其中一个窗口并重扫。

### T04 自动记录生命周期

- [ ] 启用插件后的默认运行状态与产品设计一致。
- [ ] 状态条持续显示记录状态。
- [ ] 分类暂停不会影响未暂停来源。
- [ ] 暂停/恢复后游标续接。
- [ ] 重启不重复写入事件。
- [ ] 源被截断、替换或旋转时行为明确。
- [ ] 卸载插件停止后台服务但不破坏其他插件。
- [ ] 现有 recorder 测试没有被删除或弱化。

**重点数据测试**

- 同一日志扫描两次。
- 先写 100 行，再追加 10 行。
- 暂停后追加，再恢复。
- 同时存在 NX 与 PowerMill 输入源。

### T05 日志查询与筛选 API

- [ ] 组合筛选使用 AND/OR 规则有文档。
- [ ] “仅手动 + L2 + 指定实例”返回准确。
- [ ] 多选模式不会退化成错误的字符串包含。
- [ ] 游标分页在相同时间戳下不丢失、不重复。
- [ ] 无效参数返回 4xx，不返回空 200 掩盖问题。
- [ ] 空筛选保持原有 API 行为。
- [ ] 查询计划使用索引，无全表高频轮询。

### T06 日志中心 UI

- [ ] 来源模式与 L0-L4 是两个独立控件。
- [ ] 有“仅手动”快捷入口。
- [ ] 筛选状态刷新后可恢复。
- [ ] 表格动态内容不会改变列宽和工具栏尺寸。
- [ ] 详情使用抽屉/面板，不新建窗口。
- [ ] 500 条以上不会一次性创建全部 DOM 节点。
- [ ] 错误、断连和无匹配状态可以区分。
- [ ] 所有图标按钮有工具提示或可访问名称。

### T07 会话时间线

- [ ] 会话归属优先级符合实例、项目、显式标记、时间顺序。
- [ ] 多实例交错日志不会被合并。
- [ ] 合并和拆分有版本或撤销路径。
- [ ] 会话仅引用事件 ID，不复制并漂移原始事件。
- [ ] 对比结果包含公共步骤、缺失步骤、参数差异和耗时。
- [ ] 相同输入得到相同会话 ID/结构。
- [ ] 专家标签只来自明确的用户操作。

### T08 重复流程学习

- [ ] 匹配基于规范动作和结构签名。
- [ ] 引号、路径和数值变化不会错误拆分同一流程。
- [ ] 返工/探索步骤不会被当作稳定主流程。
- [ ] 参数类型推断可解释并有来源样本。
- [ ] 支持度分母定义清楚。
- [ ] 候选排序是确定性的。
- [ ] 空日志、单会话、完全不同会话行为合理。
- [ ] 10,000 会话测试在预算内。

### T09 配方编辑器

- [ ] 配方步骤、参数、条件、版本和来源模型完整。
- [ ] 修改任何执行相关字段会更新 recipe hash。
- [ ] 保存创建新版本，不覆盖旧版本。
- [ ] 每一步可以追到来源事件和会话。
- [ ] PowerMill/NX 预览由产品适配器生成。
- [ ] 特殊字符、引号、Unicode 和控制字符处理正确。
- [ ] 三栏布局在窄屏退化为页签或纵向布局。
- [ ] 不出现卡片嵌套和多个浮动窗口。

### T10 PowerMill 适配器

- [ ] 没有修改 NX parser 来处理 PowerMill。
- [ ] `.mac / .log / JSONL` 路由明确。
- [ ] 引号内空格和参数顺序保留。
- [ ] 宏缺失默认值在结果中可见。
- [ ] 每个实例使用独立连接/队列。
- [ ] 超时、断连和错误响应进入统一 `CommandResponse`。
- [ ] 未配置真实 API 时不会声称 live 已连接。
- [ ] 版本差异通过 fixtures 或实机矩阵验证。

### T11 NX 适配器

- [ ] Journal 只由 AST 读取，从未执行。
- [ ] Builder 生命周期和 Undo Mark 映射合理。
- [ ] `FindObject` 录制 ID 没有直接升级为稳定选择器。
- [ ] 目标版本以本机 stubs 为准。
- [ ] NX 专属动作使用 `nx.*`。
- [ ] PowerMill 输入不会进入 NX adapter。
- [ ] 现有 NX pipeline 和性能测试不退化。
- [ ] 异常 Python 语法返回诊断，不导致进程退出。

### T12 命令中心与 dry-run

- [ ] 任务显式携带产品、版本和 `target_instance_id`。
- [ ] 不存在“默认发送到前台窗口”的分支。
- [ ] 每实例队列串行，不同实例可以隔离运行。
- [ ] 取消、超时、断连和重试状态明确。
- [ ] 响应包括原始结果、结构化结果、耗时和 DiffReport。
- [ ] UI 在运行前和运行后都显示目标实例。
- [ ] 项目快照差异可以复现。
- [ ] 机床 NC/postprocess 输出仍被仓库现有边界阻止。

**P0 场景**

同时创建两个同名项目、不同 PID 的实例，确认命令只进入指定 PID/窗口。

### T13 Codex 插件与 Skills

- [ ] `.codex-plugin/plugin.json` 合法，插件 ID 和版本一致。
- [ ] marketplace 条目、cachebuster 和重新安装流程已执行。
- [ ] Skill 指令与真实脚本/路径一致。
- [ ] NX Skill 不引用 PowerMill parser，反之亦然。
- [ ] 上下文包字段稳定且有 schema/测试。
- [ ] Codex 返回可以机器读取，不依赖自由文本解析。
- [ ] fixture 演示不会调用真实 CAM live 项目。
- [ ] README 与 Skills 版本同步。

### T14 诊断、性能与任务统计

- [ ] 指标口径和采样周期有文档。
- [ ] 指标采集不在 UI 主线程执行重查询。
- [ ] 100,000 事件导入和查询结果可复现。
- [ ] p50/p95 的计算方法正确。
- [ ] 单实例故障不污染其他实例指标。
- [ ] 重连、重扫、取消和导出操作都有反馈。
- [ ] 诊断包不包含无关构建文件。
- [ ] 统计 API 与页面数字一致。

### T15 集成演示与发布

- [ ] 从空白安装注册表开始可以完成全流程。
- [ ] 多实例、自动记录、仅手动筛选、L2 会话、学习、配方、Codex、dry-run 全部出现。
- [ ] 演示不依赖开发者机器上的偶然状态。
- [ ] 所有 fixture 和启动命令进入仓库。
- [ ] 根测试与 UG 测试全部通过。
- [ ] README、架构、MVP、产品方案、任务书、manifest 和 Skills 版本一致。
- [ ] `git diff --check` 通过。
- [ ] 工作区无日志数据库、缓存和临时截图。
- [ ] GitHub 分支包含完整提交和发布说明。

## 12. MVP 总体验收

只有同时满足以下条件，12 周 MVP 才能进入样板试点：

- PowerMill/NX 多实例数量和目标归属正确。
- 记录插件可以自动运行、暂停、恢复和增量续接。
- “仅手动”和 L0-L4 筛选可以组合使用。
- 至少三类重复流程可以生成带来源和参数的配方。
- PowerMill 与 NX 解析器边界通过自动测试。
- Codex 能返回结构化审阅结果。
- 指定实例 dry-run 可以返回响应和 DiffReport。
- 性能达到产品方案中的首版预算。
- 全量测试、文档、插件 manifest 和 Skills 同步完成。
