# CAM Automation Studio：项目评估、CAD/CAM 技术调研与演进方案

评估日期：2026-09-29。范围：当前工作区（含未提交的 Cimatron 扩展），基础提交 `1d96f69`，项目声明版本 `0.6.1`。本次只新增评估资料，没有修改业务实现。

## 1. 决策建议

**保留现有离线工作流内核，把下一阶段资源集中到“一个真实宿主、一类零件、可测量的工艺复用闭环”。** 推荐定位为面向模具工厂的本地工艺复用与验证工作台。

现有项目已经覆盖采集、静态解析、会话比较、重复流程挖掘、参数化配方、流程图、版本差异和审阅门禁，具备继续演进的基础。决定下一阶段价值的是：系统能否理解当前零件、正确找到加工对象、解释历史工艺为何适用，并用实际验证结果支持建议。

建议的技术组合：

- 产品原生 API 提供真实对象与状态；保持 NX、PowerMill 解析与传输隔离。
- 现有 ActivityEvent、FlowGraph、Recipe 继续作为可审阅、可追溯的主干。
- 增加几何与制造上下文、语义对象选择器、历史案例检索和结果证据。
- AI 负责解释、检索和提出结构化修改；确定性代码负责类型、单位、适用条件、能力和状态检查。
- 后续如需独立 CAD 能力，先用 CadQuery/OCCT 实验夹具、软爪、标准辅助件，逐项验证宿主导入效果。

暂缓自研通用 CAD 内核、大规模基础模型训练、全产品全版本覆盖、五轴自由曲面全自动编程和大幅重写前端。现阶段这些投入难以验证收益。

本文讨论的“先进实现”是截至访问日、可核实的代表性路线；没有跨所有产品的独立统一实测，不能给出绝对第一名。厂商效果数字不作为本项目收益保证。

### 2.1 为什么“录制很多日志”还不够

日志通常描述发生了什么，未必完整记录当时的默认设置、几何选择、毛坯、夹具、刀柄、材料和操作者的取舍。相同动作序列可能用于不同加工任务；参数变化也可能来自错误或临时试探。

当前学习器的支持度可以表示多个独立会话中出现了同一结构，但不能直接解释为加工成功概率。应把以下信息分别记录：出现次数、解析可信度、对象绑定是否唯一、专家是否接受、仿真结果以及现场结果。

## 3. 优先处理的问题

### P0：Cimatron 的 Flow 能力声明与产品分派不一致

`product_catalog.py:72` 声明 `flow_import_supported=True`；`integrations.py:43` 把 Cimatron 加入支持产品。可是 `_map_offline_flow_source`（约 1092 行）只有 `if product == "nx"`，其他产品全部进入 `PowerMillFlowImporter`。

本次直接离线调用该映射函数，传入 Cimatron Python 风格源代码，得到：

```text
PowerMillOfflineImportError: Non-PowerMill input is not accepted by the PowerMill parser.
```

这证明错误分派存在；并不表示真实宿主已发生跨产品执行。建议先把能力标为不支持，再通过显式 adapter registry 接入独立 Cimatron Flow mapper。禁止用 `else` 表示“其余产品都是 PowerMill”。未知产品应在产品边界明确拒绝。

### P0：Cimatron 插件交付不完整

当前目录有 `.codex-plugin/plugin.json` 和五个 Skills，但未找到工作台所需的 `app-plugin.json`、Flow capability manifest 和产品测试。`PluginManager` 只扫描 `*/app-plugin.json`，因此 Codex 目录出现第三产品不等于工作台插件已经可安装。

应把“插件可发现、静态解析、Flow 导入、配方预览、只读连接、实际动作”拆成独立能力状态。现有 `command_tasks_supported=False` 是合理保守声明，不应为了展示完整而开放未实现能力。

### P1：Cimatron 静态解析覆盖面需要真实样本验证

Python 实现使用 `ast.walk` 后按行号/调用名称排序；它提取的是语法中出现的调用，不能解释为实际执行顺序。未调用函数内的调用、条件分支、嵌套调用都需要保留上下文。

C# 实现逐行正则匹配，并使用 `split("//", 1)` 去注释，对多行调用、字符串中的 `//` 和嵌套表达式存在误解析风险。建议对无法证明语义的部分保留原文/opaque 节点；达到真实样本覆盖需求后，引入 Roslyn 或合适的 C# AST，而不是继续叠加正则。

Cimatron 官方仅说 Journaling 支持部分工具，不能推断所有 Part/Assembly/NC 动作均可录制。样例调用也需目标版本 SDK 或真实录制文件支撑。[S7]

### P1：缺少几何与制造上下文

已有 `before_snapshot`、`after_snapshot` 和 selector 建议是扩展点，但不足以回答“这条配方现在作用于哪几个面、为什么刀具可达、什么状态变化会让审批失效”。这是从日志复用走向可靠工艺复用的主要技术差距。

### P1：可复现交付与模块边界

本机环境导入污染说明运行与测试入口需要隔离。建议标准化独立 venv、固定运行时和 CI；包构建时验证 manifest、schemas、静态界面和插件资源是否包含，不能只确认源码目录可以启动。

当前大文件包括 `flow_service.py` 2590 行、`codex_bridge.py` 2140 行、`flow_validation.py` 2004 行、`web_server.py` 1809 行、`integrations.py` 1790 行。行数不直接等于质量问题，但产品扩展反复触及共享大模块，已经显露维护成本。优先抽出产品注册、宿主协议、审阅证据和 API DTO，保留现有外部接口与测试。

### 4.1 值得采用的共同方法

先进系统的共同方向是：**工程语义表示 → 受约束的候选 → CAD/CAM 原生工具求值 → 检查结果 → 人工选择与反馈。**

三个概念需要分清：

- **CAD 建模**：形状、草图、约束、特征、装配与设计意图。
- **CAM 规划**：装夹、刀具、余量、策略、刀路与加工条件。
- **验证**：几何正确性、过切/残料、碰撞、机床运动和现场批准。

项目目前最强的是 CAM 流程表达与审阅。CAD 能力应首先服务于当前零件理解、对象选择和辅助件生成。原生宿主仍负责其精确模型和 CAM 求解；浏览器里的三角网格主要负责显示与选择反馈。

### 4.2 为什么不建议直接采用“LLM 生成脚本并运行”

脚本语法合法不能证明目标对象、单位、刀具和夹具正确。代码可以运行、实体可以生成、模型符合设计要求、加工可以通过仿真，是不同层次的成功标准。BenchCAD 对当前模型的结果也支持把这些指标分开。[S13]

建议 AI 只提出明确 schema 的计划或 graph patch，禁止通过未受约束的 Python/宏入口抵达宿主。若未来研究运行生成 CAD 程序，应在独立受限 worker 内执行，限制文件、网络、进程和资源；AST 检查本身不构成执行沙箱。

## 5. 建议目标架构

```mermaid
flowchart LR
  A[真实 Journal / 宏 / 只读宿主快照] --> B[产品独立适配器]
  B --> C[ActivityEvent 与来源证据]
  B --> D[几何和制造上下文]
  C --> E[历史工艺案例库]
  D --> E
  E --> F[检索候选与规则过滤]
  F --> G[AI 解释和结构化修改提案]
  G --> H[FlowGraph / Recipe 与确定性验证]
  H --> I[人工审阅与差异预览]
  I --> J[隔离验证项目 / 宿主验证证据]
  J --> K[结果标签与案例反馈]
  K --> E
```

图中的真实宿主快照、几何上下文、案例结果闭环和隔离验证项目均为新增能力，不能理解为目前已经实现。现有 Flow fixture preview 保持原有语义，不把它偷偷升级成真实动作。

### 5.1 产品适配层

建议定义统一接口，但能力由产品逐项声明：

```text
describe_capabilities(target_version)
read_project_snapshot(explicit_instance)
list_cam_objects(snapshot)
resolve_selector(snapshot, selector)
compile_review_draft(recipe, context)
read_validation_evidence(validation_run)
```

NX parser 继续位于 `plugins/ug-cam-copilot/src/ugcam_ai/adapters/nx_journal.py`；NXOpen 连接逻辑放独立 transport。PowerMill 解析保留在现有 adapter/profile，未来原生桥接单独实现。Cimatron 同样拥有自己的 adapter，不能复用另一产品的语法分支。

NX 与 PowerMill 的跨产品复用应发生在加工意图、参数和前置条件层，之后分别编译和验证；不承诺宏与 Journal 的逐句互译。

原生桥接建议使用宿主内薄层插件与本地服务通信：明确实例握手、版本与文档 ID，受宿主线程规则约束的队列，结构化查询，不暴露任意代码执行接口。Windows COM/线程亲和性、多个文档/窗口、异常模态框和超时都要实机验证。检测进程的 PID/窗口句柄只用于发现，不能替代连接会话身份；重启后的会话 epoch 防止复用旧绑定。

PowerMill 官方 API 仓库已提供宏命令自动化路径，但仓库中的旧构建配置不能视为当前安装版本的兼容保证；DLL、COM、API 方法和许可需对照现场版本。[S14]

### 5.2 几何与制造上下文

新增独立 `ManufacturingContext` 合同，由 Recipe/Event 的可选引用关联，避免向所有历史事件塞入完整模型：

| 数据 | 最低需要记录 | 用途 |
|---|---|---|
| 文档身份 | 产品、精确版本、实例会话、文档 revision/hash | 阻止旧状态误绑定 |
| 单位与坐标 | 长度/角度单位、坐标系、变换、几何公差 | 消除毫米/英寸和局部/全局坐标混淆 |
| 工件/毛坯/夹具 | 对象引用、几何摘要、装夹方向、区域 | 判断工艺适用范围 |
| 几何特征 | 面/边类型、面积、法向、曲率、邻接、孔/槽/型腔语义 | 选择对象与案例匹配 |
| 刀具组件 | 刀具、刀柄、伸出、直径、刃长、实际可用状态 | 可达性及碰撞输入 |
| 工艺条件 | 材料、机床、余量、表面要求、公差及权威来源 | 过滤不适用历史案例 |
| 证据 | 来源、采集时间、缺失字段、人工确认 | 暴露未知条件 |

优先读取原生特征/PMI/属性；缺失时再用确定性几何规则推断孔、平面、槽等。保留“原生事实”和“推断”区别，避免把视觉判断写成精确制造要求。

### 5.3 语义对象选择器

对象定位建议顺序：受控业务属性/特征关系 → 经验证的宿主引用 → 带公差的几何查询 → 人工指定。不能永久依赖录制的面编号或 FindObject 字符串。

示例选择意图：“工件 A、位于装夹坐标系上表面、直径范围已确认的通孔组”。解析器返回匹配集合、依据和歧义；目标要求唯一却出现多个对象时必须停止。每次几何 revision 变化都重新绑定并检查，不能用历史匹配分数直接沿用。

### 5.4 AI、检索与结果反馈

第一版从结构化过滤和 SQLite FTS 开始：同产品、版本、材料族、加工类型、刀具可用性为硬条件，再按特征尺寸、装夹方向、余量和历史结果排序。有证据说明关键词/结构检索不够时，再加本地向量索引或重排模型。

每个候选解释：来源案例、可复用步骤、需要调整的参数、未知条件、拒绝原因。用户接受/修改/拒绝及原因独立记录；不能把“采纳了建议”自动当成“加工成功”。

AI provider 作为可替换层，记录模型/提示模板/检索数据版本、输入上下文 hash 和输出 patch。任何模型都先通过同一离线评测；没有数据前，不依据排行榜选择一个模型并宣称可以处理全部 CAD/CAM。

### 5.5 验证证据闭环

把验证结果绑定到 recipe hash、模型 revision、目标版本、机床/刀具/夹具快照和验证器版本。上述输入变化后，旧结果失效。分别展示：

1. schema、单位、能力、对象绑定检查；
2. 原生 CAD/CAM 对象生成和状态差异；
3. CAM 仿真、过切/残料、碰撞与机床相关检查；
4. 人工审阅与现场批准。

新生产动作仍按仓库要求保持 dry-run，直到对应人工与制造门禁满足。fixture 测试不能将真实仿真标记为通过。不得由学习日志直接生成或下发 machine-ready NC。

### 5.6 CAD 与前端的渐进演进

- 保留 Python 服务、现有 SQLite 与纯前端界面，先通过 profile 修复热点。
- 引入只读 3D 视图时使用 Three.js 等显示网格，并维护选中面到宿主对象的映射；网格精度不能作为尺寸验证依据。
- 独立 CAD 试验选择 CadQuery/OCCT；若复杂 builder 工作流成为需求再比较 build123d。后者是待评估备选，本次未做专项核验。
- 对流程复杂度增长，评估显式状态机与 React Flow 等组件；只有现有代码维护成本成为瓶颈时才迁移，保留 FlowGraph 合同和语义测试。
- 对外工具协议以后可以包装现有结构化服务；换协议不会自动补齐几何、制造知识或安全状态。

## 6. 分阶段演进计划

以下周期假设 2 名开发者、1 名可持续参与的 CAM 工程师、可使用的目标宿主许可与真实样本。按工作量估算，不是交期承诺；单人兼职应减小范围并延长周期。

| 阶段 | 时间估算 | 交付物 | 通过条件 |
|---|---|---|---|
| **0.6.2 稳定基线** | 1–2 周 | 隔离测试入口、产品注册/能力一致性、Cimatron 关闭未实现能力或补齐包、性能分析 | 干净环境全测试通过；未知产品绝不进入其他 parser；安装与能力可验证 |
| **0.7 真实只读连接** | 2–4 周 | 一个主力产品、一个精确版本、实例握手、项目/工序/刀具快照、来源关联 | 与人工核对至少 20 个真实项目；双实例零串线；断连/换项目可检测；没有修改宿主 |
| **0.8 几何驱动工艺复用** | 3–4 周 | ManufacturingContext、选择器、案例检索、10 个专家模板、候选对比界面 | 在独立留出项目上，适用/不适用能区分；高风险歧义全拦截；记录人工修正时间 |
| **0.9 验证闭环试点** | 4–6 周 | 隔离验证项目方案、结果导入、审批失效规则、真实失败恢复用例 | CAM 工程师按预定检查清单验证；异常可停止；状态和证据一致；满足仓库生产门禁 |
| **1.0 有界商业试点** | 6–10 周 | 两家试点、固定支持矩阵、安装诊断、备份恢复、付费价值报告 | 持续使用与净节时达标；支持成本可承担；确认需求后再扩第二主力宿主 |

前三个月建议只承诺推进到 0.8 或启动 0.9；1.0 和后续产品扩展不应被塞进同一个十二周全包承诺。

### 6.1 主力产品与场景

默认商业切口：PowerMill 模具工厂的同类型腔加工工序模板复用与参数检查，先限定三轴、明确工装和已知刀具。当前 PowerMill 文本资产链路较完整，符合模具场景。

如果真实 NX 项目、SDK 与现场工程师更容易获得，则优先 NX 的孔系/型腔工序复用；成功打通现场比维持预设产品顺序更重要。两条代码线保持合同兼容，商业验收聚焦一条。

Cimatron 2026 Journaling 值得保留为独立实验接入，但先补齐包、能力与真实样本测试。当前 AGENTS.md 只明确 NX/PowerMill 产品命名空间，第三产品正式纳入时需同步更新产品边界与兼容性政策，保留原有合同保证。

### 6.2 第一个可演示的真实任务

输入一个新零件、选定加工特征和工装上下文；系统找出三个历史相似案例，显示复用依据、刀具条件与参数差异；工程师选择并修订一个配方，得到审阅草稿及当前状态检查结果。之后由受控验证流程回传仿真证据，沉淀为下一次检索依据。

这个任务同时验证用户是否愿意提供历史资产、几何上下文是否足够、模板是否有用和审阅是否省时，比增加几十个菜单更能判断项目方向。

## 7. 评测与商业验证

建议起始数据：30–50 个经授权的真实项目、三个明确零件族、每族多次专家操作和失败样本。数量是启动建议，不是统计充分性保证。

按项目/零件族拆训练或案例库与测试集；同一零件的小改版不要泄漏到两边。先做规则检索和专家模板基线，再比较加入 AI 的增量收益。

| 指标 | 测量方式 | 初期目标建议 |
|---|---|---|
| 解析覆盖 | 可解释操作数 / 应解释操作数；unknown 单列 | 目标场景 ≥95%，不支持部分明确展示 |
| 对象绑定 | 人工标注下的正确、歧义、拒绝与误绑定 | 已知高风险歧义样本 100% 拦截；有限测试零误绑定不宣传绝对安全 |
| 推荐效果 | 留出项目的 top-3 专家可接受比例、需要修改步骤数 | 先建立人工/规则基线，再设 AI 提升目标 |
| 净节时 | 包括录入上下文、审阅、修复和验证的总用时 | 中位数相对人工降低 ≥30% 作为试点继续条件 |
| 验证有效性 | 结果是否绑定正确 revision、recipe 与工装 | 陈旧/缺失/错误绑定证据全部拒绝 |
| 恢复能力 | 断连、宿主忙碌、版本错配、模型变化、取消 | 每个明确故障有可恢复状态，禁止默默续跑 |
| 经济价值 | 月节时 × 人工成本 − 授权/部署/维护成本 | 企业实际愿付费，且现场支持成本可控 |

如果用户认可资产搜索与差异审查，但自动参数化效果不足，可以先交付“历史工艺资产检索与审阅”版本。若提供上下文和审核的耗时持续超过节省时间，应收缩场景，不能用更多 AI 功能掩盖负收益。
